## 3. Architecture and reuse

PostgreSQL remains authoritative. ApplicationService extends ProjectService and uses the existing
security context, tenant governance lock, owner-Project write checks, sharing, resource lifecycle,
folder identity and audit methods. QueryService and ActionExecutionService are composed through their
existing transaction-session interfaces. Application gateways add resource/dependency checks and
version pins, then delegate canonical queries, preview and execution to those services. There is no
second query/action/reasoning engine, privileged execution identity, queue, database or object store.

The strict schema and backend validation preceded persistence. The standalone renderer preceded the
structured editor. React Flow was evaluated against the page-layout problem and was unnecessary;
explicit tree, parent and move controls provide keyboard authoring. The editor and runtime consume
one generated canonical document type. SDK methods/hooks are generated by the existing pipeline.

## 4. Resource and database model

APPLICATION is a registry kind with stable tenant/resource UUID, owning Project, optional folder,
name, description, provenance, revision and ACTIVE/ARCHIVED lifecycle. Existing folder moves and
shares retain identity. `application_drafts` holds one private current document per tenant/app/actor,
with explicit revision CAS. `application_versions` holds immutable UUID/sequence, format, document,
SHA-256 digest, dependency manifest, creator and publication time. Tenant-qualified FKs, unique
sequence/digest constraints, size guards, active-resource guards and immutability triggers apply.
Publication validates the locked saved revision and dependencies and inserts version/audit atomically.
Concurrent identical publications return one version; a failed audit after insertion rolls back.

## 5. Schema and widget catalog

Format v1 forbids unknown fields, unsupported kinds, unsafe object keys and executable configuration.
Application-specific model names preserve existing public OpenAPI component identities. Stored query
ASTs use the canonical validation schema identity; response models retain normal serialization.
Canonical JSON sorts object keys and preserves semantic list order; the digest includes defaults.
Published formats never migrate in place. Future formats fail closed. Identical canonical content
returns its existing version, including when revisited after publishing another configuration.

Stable IDs identify pages, widgets, states, dependencies, sources, actions and interactions. Parent IDs
represent a bounded layout tree; duplicate IDs, missing references, cycles, excessive depth, type
mismatches, unsupported configuration and wrong source result shapes prevent publication. Runtime
state propagation is single-step and never recursively emits events. Visibility uses equals/not-empty.

The 18 widget kinds are heading, text, label, metric, property, detail, table, list, status, navigation,
section, text input, numeric input, checkbox, select, date input, parameter form and action button.
The registry has exhaustive typed renderers. Inspectors configure shared and widget-specific fields;
backend validation rejects incompatible combinations. Object lists use semantic lists, tables have
accessible row-selection and server-sort controls, and inputs use semantic labeled controls.

## 6. Runtime renderer

The authenticated route `/applications/{application}/versions/{version}` independently resolves the
current authorized manifest. It supports multiple pages, responsive rows/columns/grids, spacing and
alignment, selected object details/properties/status, parameter/filter/form state, visibility, explicit
navigation, sorting, cursor pagination, loading/error/empty states and action feedback. Only active-page
sources load, source IDs deduplicate requests, four workers bound concurrency and 150 ms debounce
coalesces state changes. Page/source changes abort stale reads; results replace previous pages.
No polling, full-collection browser filtering, persistent private cache or arbitrary event code exists.

## 7. Visual editor

Studio Project navigation creates and opens applications. The editor provides page titles/descriptions,
home selection, page parameter declarations, palette, component tree, parent placement, reordering,
deletion, inspector controls, authorized dependency discovery, query projection/sort/page-size/link/
filter controls, typed binding forms, published Action Type parameter forms, backend diagnostics,
draft save, validated preview, publication and immutable history links. Preview and publication use
the same document. Unsaved, saved, invalid and published states are distinct. Conflicts never silently
overwrite drafts. Keyboard insertion, configuration, movement and deletion are exercised in-browser.

## 8. Query/action and manufacturing integration

Runtime query gateways resolve configured structured sources, filters, sort, traversal, aggregates and
cursor pages, then call canonical QueryService. Browser preview uses generated query/aggregate SDK
capabilities. No raw SQL or unbounded download is accepted. The manufacturing preset uses the actual
`machineId`, `machineName`, `operationalStatus`, `temperatureCelsius` vocabulary, selected object ID/
revision bindings, optional `locatedInFactory` traversal, canonical count, status input and the actual
published `UpdateMachineStatus` Action Type. It supplies Operations and About pages.

Preview is advisory and side-effect free. Execution uses canonical parameter checks, current policy,
preconditions, optimistic revisions, idempotency, object edits, transactions, audit and outbox behavior.
Confirmation is explicit. Execution feedback includes its audit-addressable execution ID; successful
mutations clear selection and refresh active data. Preview grants no later execution authority.

## 9. Authorization

App/resource access and ontology authority are cumulative. Every manifest/query/action operation
rechecks current registry visibility, active Project/share state and exact published ontology pins.
Schema access is independent of Project grants. Canonical services enforce object/property/link/action
policy. Cross-tenant IDs do not resolve. Sharing an app shares no dependency; sharing a dependency
grants no data/action permission. Fixed dependency diagnostics avoid private names/schema leakage.
Design/publication validation inspects authorized schema metadata without reading operational rows.
Browser credentials remain HttpOnly/server-side behind the existing CSRF and expected-tenant BFF.
SDK invalidation removes private application views on session/permission changes; stale requests abort.

## 10. Dependency and version policy

Dependency manifests record registered resource UUID, ontology identity, exact schema version and
`exact_active` policy. Runtime requires the pinned version to remain active; schema activation requires
explicit rebinding/republishing. This deliberately conservative compatibility policy avoids following
mutable drafts. Historical publication identities/documents remain stored; revoked/incompatible
references fail closed at retrieval/runtime. Old authorized published-schema drafts remain recoverable.
Live object values are current operational values, not immutable historical values.

## 12. Limits and observability

See [phase-19-limits.md](phase-19-limits.md). Raw POST/PUT payloads are bounded before FastAPI JSON
parsing by the existing middleware; documents are bounded before validation and after default expansion.
Existing action deadlines are reused for a five-second publication SQL deadline after governance lock

and retained publications have explicit bounds. React escapes text; no HTML/source interpreter exists.
Existing HTTP/BFF traces, query/action error metrics, application audit events and visible data/action/
publication diagnostics provide basic observability. No analytics platform is added.

## 18. Known limitations and production status

Initial v1 is a structured page/tree editor, not pixel-perfect desktop publishing or full Workshop.
No real-time merge/history for private drafts; stale-write recovery requires reopening the editor. Current history UI opens 50 versions; API history is
paginated. Inputs/action-binding forms focus on scalar and selected-object values; there is no arbitrary
JSON/array form designer or expression scripting. Filter controls author equality bindings; canonical
structured filter ASTs remain the API contract. State/page parameters are application-local; no URL
parameter serialization, external embedding or independent hosting is provided. Dependency discovery pages owned root assets and explicitly shared assets; it has no recursive owned-folder picker. Property/metric names
can be entered explicitly and are validated against current authorized schemas. Version pins require
republishing after any ontology activation, including additive changes. No chart or asset-upload widget,
Function execution, generalized OAuth client registration or standalone Action Builder expansion.

Container build validation is incomplete because the pinned base image was unavailable locally and
registry resolution stalled. Local successful builds/tests do not establish production readiness.
§23B release/security/target/provider/capacity/recovery/organizational gates remain mandatory and BLOCKED.
